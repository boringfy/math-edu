# App Privacy answers — Have Fun Learning

What to tick in App Store Connect → App Privacy, and the line in the code that
justifies each answer. Apple compares these answers against what the binary
actually does, so every row below is traceable.

## The short version

The app has **no advertising SDK, no analytics SDK and no third-party advertising tracker**.
Nothing is sold, nothing is shared with data brokers, and nothing is used to
follow a child across apps. Optional first-party usage counts are sent only
after the first-launch prompt is accepted and can be disabled in Settings.
Apple-device progress is stored in the family's
private iCloud key-value store, which the developer cannot browse. A
pseudonymous device identifier accompanies feedback someone chooses to send.

**Tracking: No.** Nothing is linked to third-party data for advertising, so the
App Tracking Transparency prompt is not required and is not shown.

## Data types to declare as collected

| Apple data type | Why | Linked to user | Used for tracking |
| --- | --- | --- | --- |
| Identifiers → **Device ID** | A UUID used for feedback (`mathquiz:deviceId`), and a separate random per-install usage ID minted only after analytics consent. Neither is the IDFA or IDFV. | Yes | No |
| User Content → **Other User Content** | The free-text body of a bug report or a "suggest a kind of problem" form, only when a grown-up chooses to send one. | Yes | No |
| Usage Data → **Product Interaction** | Lesson progress in private iCloud; anonymous level-planning summaries for app functionality; and, only after consent, app-open and completed-lesson events with subject, platform, app/OS versions and a random install ID sent to Hashfront for analytics. No names, answers or scores in usage events. | Yes | No |
| Diagnostics → **Other Diagnostic Data** | The client IP address is stored with each report, for rate limiting and to tell one sender from another. | Yes | No |

**Purpose:** App Functionality for progress, planning and feedback. Also select
**Analytics** for the optional Product Interaction and install ID usage data.
No advertising or cross-app tracking.

## Data types NOT collected — and the reason each one is safe to answer "No"

| Not collected | Why the answer is genuinely No |
| --- | --- |
| **Audio Data** | Read-aloud sets `requiresOnDeviceRecognition: true` (`frontend/src/lib/speech.ts:98`), so Apple's Speech framework never sends audio to a server. No recording is written to disk and no audio leaves the device. A test pins the flag (`src/components/__tests__/readAloud.test.tsx:101`), so it cannot be turned off by accident. |
| **Contacts, Photos, Location, Health, Financial** | No permission is requested and no API is called. The app requests only microphone, speech recognition and optional notifications. |
| **Name, Email, Phone** | There is no sign-up. The Account row in Settings shows "this device only" until a backup is made. |
| **Search History, Browsing History** | No browser and no search. |
| **Advertising Data** | No ad SDK is linked. |
| **Crash Data / Performance Data** | No crash reporter is linked — no Sentry, no Crashlytics, no Firebase. Worth knowing this is a deliberate cost: crashes in the field are invisible. |

## The microphone and speech permission strings

Already written in `app.json` and worth keeping as they are, because Apple reads
them and because they are true:

- **NSMicrophoneUsageDescription** — "Have Fun Learning listens while you read a story out loud, so it can light up the words it hears."
- **NSSpeechRecognitionUsageDescription** — "Have Fun Learning checks which words you read out loud during reading practice."

Reading aloud still requests on-device recognition; the permission text focuses on why access is needed.

## iCloud and reminders

Progress is encoded into one value in `NSUbiquitousKeyValueStore` and merged
on launch, resume and after progress changes. It contains local player names,
grades, lesson history, stars, coins and preferences. It is private to the
user's iCloud account and is not available in the developer's CloudKit
console. Daily reminder notifications are scheduled locally at the time the
adult chooses; no push token is created and no reminder activity is sent to a
server.

The level planner receives an anonymous learning summary to prepare and refresh
the next five math or logic levels. It receives no profile name, stable device
identifier, IP stored by the app, or raw answer text. The backend necessarily
sees the connection IP in transit but does not persist it for level planning.

## The one thing that needs a decision: the AI tutor

After two wrong answers of the same kind, the app can show a short worked
lesson. That text is generated by a language model on the server, not on the
device — the question is sent out, the explanation comes back.

Two facts that limit the exposure:

1. **The model never writes questions or answers.** It explains a method using
   different numbers. Every number a child is graded on comes from a
   deterministic generator in the app.
2. **It is off on the production server right now.** No `TUTOR_LLM_*` key is
   configured at `math-edu.hashfront.com`, so `/v1/explain` returns
   `503 tutor is not configured` and the app simply doesn't show the tutor.

So for this submission the feature is dark. That is the simplest thing to
review. **If the key is added before release**, then:

- the outbound question text should be declared (it is not personal data, but it
  is data leaving the device to a third-party model provider), and
- the age rating questionnaire's generative-AI questions have to be answered
  honestly rather than left at "None".

Apple's rules for generative AI shown to children have been moving, so check the
current questionnaire text at submission time rather than trusting a summary
written here. My recommendation: **ship 1.0 with the tutor dark**, and turn it
on in 1.1 as a deliberate, separately-reviewed change.

## Kids Category — recommend NOT opting in for 1.0

It is tempting, and it is a real restriction. Opting in commits the app to:

- no third-party advertising or analytics — **already true**;
- a parental gate in front of anything leaving the app — **already true, there is nowhere to go**;
- and no collection of persistent identifiers from children.

That last one is the problem. The app stores a persistent device UUID and an IP
address alongside bug reports. There is a reasonable argument that both fall
under COPPA's "support for internal operations" exemption, because they exist
for rate limiting and de-duplication rather than profiling — but it is an
argument, and it is one you would be making to a reviewer rather than avoiding.

**Recommendation:** list under **Education**, age rating **4+**, and skip the
Kids category for the first release. Nothing about the app changes; the listing
is simply not making a claim it would then have to defend. Revisit it once the
identifier story is simpler.
